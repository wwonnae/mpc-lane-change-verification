## 1. 개선 항목

### I1 — rate limit·δ_prev 인지 MPC (`IMPROVEMENT_BACKLOG.md` 후보8 전반부, 하드 유지)

- **변경**: `solve()`가 실제 `delta_prev_deg`를 새 인자로 받고, QP에 하드 제약 2종류
  추가: `|δ_0-δ_prev|≤10°/step`(매 solve 갱신), `|δ_i-δ_{i-1}|≤10°/step` i=1..N-1(고정
  계수, l/u만 온/오프로 토글). 새 변수 없음(z 벡터 불변) → QP는 여전히 볼록
- **근거**: S6 seed=6 — `solve()`가 `delta_prev`를 몰라 매 step 즉시 원하는 각도를
  낼 수 있다고 낙관적으로 재계획, rate limit에 막혀 계획보다 계속 뒤처지다 QP 자신도
  뒤늦게 infeasible 발견
- **예상 효과**: QP의 "이번 step 실현 가능성" 판단이 실제와 일치 → 낙관적 재계획으로
  인한 지연 회복 없음
- **부작용 위험**: 평상시에도 QP가 더 자주 포화·infeasible로 갈 수 있음(paper 비열화
  조건으로 확인 필수). 행 수 소폭 증가로 계산량 소폭 증가
- **고정 파라미터 변경**: 없음(rate 10°/step는 REQ-VEH-03 기존 값 재사용)

### I1b — 위치제약 소프트화 (신규, I1과 독립 플래그)

- **변경**: **조향각·rate limit(I1)은 하드 유지**, **y·ψ 위치제약만** 슬랙 변수 +
  ℓ1(선형) 벌점으로 소프트화. y_i마다 슬랙 `s_y_i≥0`을 도입해 기존 두 방향 부등식
  `lo≤y_i≤hi`를 `y_i+s_y_i≥lo`, `y_i-s_y_i≤hi` 두 개의 한쪽 부등식으로 분리(psi_i도
  동일하게 `s_psi_i≥0`). 비용에 `ρ·s_y_i`, `ρ·s_psi_i`(선형, ℓ1)를 더함. I1b가
  꺼지면 슬랙의 상한을 0으로 고정해(`0≤s≤0`) 정확히 기존 하드 제약과 같아짐 — **구조는
  항상 동일**하고 슬랙 상한(0 vs +∞)만 ablation으로 토글
- **벌점 가중치 ρ 결정 근거(exact penalty, 실험 튜닝 아님)**: ℓ1 벌점은 "정확한 벌점
  정리"(exact penalty theorem, 볼록 최적화)에 의해 `ρ ≥ ‖μ*‖_∞`(원래 하드 제약 문제의
  KKT 승수 최대 크기)이면 **하드 문제가 실현 가능한 한 소프트 문제의 해가 하드 문제의
  해와 정확히 같음**(슬랙=0)이 보장됩니다(ℓ2/제곱 벌점은 이 성질이 없어 유한한 ρ로는
  근사만 됨 — 그래서 ℓ1을 선택). 승수 상한을 다음과 같이 보수적으로 계산:
  - y 방향: 한 스텝의 비용 기울기는 `2·qy·|y-target|`, `|y-target|≤0.75`(y∈[-0.45,0.45],
    target∈{0,0.30})로 최대 `2×100×0.75=150`. 코스테이트(잔여 호라이즌 N step 누적,
    최악의 경우 선형 누적으로 과대추정)로 `150×15=2250`
  - ψ 방향: `2·qψ·|ψ|_max`, `|ψ|≤80°=1.396rad`(REQ-MPC-04)로 `2×25×1.396≈69.8`,
    누적 `69.8×15≈1047`
  - 두 값의 최댓값(2250)에 **안전계수 약 4.4배**를 적용해 **ρ=10,000**으로 확정(y·ψ
    슬랙 공통 사용 — ρ는 q벡터에만 들어가 P의 조건수에 영향 없음, 크게 잡아도 수치적
    부작용 없음)
- **근거**: 사용자 지시 — "실현 가능하면 위반 0"을 이론적으로 보장하면서, 실현 불가능한
  경우(S6류)에는 하드 infeasible/fallback 대신 "가장 작은 위반"을 QP 스스로 계산하게
  함(현재 fallback은 위치제약을 전혀 모르는 비례제어라 위반 최소화를 보장 못함)
- **예상 효과**: infeasible 발생 자체가 사실상 사라짐(슬랙이 있으면 delta bound·rate
  limit만 있는 문제는 항상 feasible) → S6류에서 fallback 대신 QP가 직접 "최소 침범"
  해를 계산. 실현 가능한 조건에서는 ρ=10,000이 어떤 실제 승수보다 크므로 슬랙=0(위반
  없음) 보장
- **부작용 위험**: 슬랙이 있으면 `solver_status`가 거의 항상 "solved"가 되어 REQ-MPC-07
  fallback·infeasible 카운트의 의미가 바뀜(위반 여부는 slack 값으로 별도 확인해야 함
  — 로깅 확장 필요, §5 판정 기준에 반영). ρ가 이론상 넉넉해도 수치오차로 아주 미세한
  슬랙(수치 잡음 수준)이 남을 수 있어 §5 허용오차(eps_abs) 기준을 그대로 적용
- **고정 파라미터 변경**: 없음. **새 파라미터 1개**(`SOFT_CONSTRAINT_PENALTY=10000`,
  위 해석적 도출로 확정, dev 튜닝 아님)

    **차체 최저점=전륜우측**, 오프셋 `L·sin(ψ)-B/2·cos(ψ)`

### I2' — I2 재도출: 헤딩 하한 추가로 마진 축소 (2026-09-23 검토 반영, 해석적)

### I3 — fallback 교체: 직전 성공 MPC 해 shift (`IMPROVEMENT_BACKLOG.md` 후보8 후반부, 수정)

- **변경(폐기 후 대체)**: "포화 방향 강제 조향" 안은 **폐기**합니다(센서 노이즈로 인한
  일시적 오판 시 급격한 조향을 낼 위험이 있어 사용자 지시로 기각). 대신 **직전
  성공(solved) MPC 해의 예측 시퀀스를 한 칸 shift**해서 재사용합니다: 마지막 성공
  solve()의 `δ*_0,...,δ*_{N-1}`을 저장해뒀다가, 이번 step이 실패하면
  `δ*_1,...,δ*_{N-1}, δ*_{N-1}`(마지막 값 반복)을 새 계획으로 채택하고 그 첫 값을
  이번 step 명령으로 사용 — 표준 MPC의 "이전 계획 재사용" 안전판. **직전 성공 해가
  아예 없으면(에피소드 시작부터 실패 등, 사실상 발생 안 함)** 기존 비례 fallback
  (K_p=1.0)으로 폴백
- **근거**: 사용자 지시(포화 강제 위험 회피) + S6 seed=6에서 기존 fallback이 QP의
  최근 "계획"을 완전히 버리고 y-오차만 보는 대신, **QP 자신이 최근에 옳다고 판단한
  방향(shift된 계획)을 계속 따르는 편이 더 안전**하다는 표준 MPC 관행과 일치
- **예상 효과**: infeasible 순간에도 급격한 방향 전환 없이 "원래 계획대로 계속" 진행
  → 노이즈에 덜 민감하면서도 y-오차만 보는 것보다 정보량이 많음(직전 계획은 이미
  동역학·목표를 반영한 궤적)
- **부작용 위험**: I1b(슬랙)가 켜져 있으면 infeasible 자체가 거의 안 생겨 I3가 발동할
  기회가 드묾(ablation으로 상호작용 확인). shift된 계획이 몇 step 연속 실패 시
  점점 "오래된" 계획이 되어 정확도 저하 가능 — 로깅에 "몇 step 연속 shift 중인지"
  기록해 관찰
- **고정 파라미터 변경**: 없음

## 2. 센서 인터페이스 확장안 (I2용)

**근거(PDF)**: p.7 "LiDAR 센서는 2D 스캔을 수행하여 주변 장애물까지의 거리를 측정" —
2D 스캔은 개념적으로 거리(range)뿐 아니라 방위(bearing)도 포함하므로, 이미 감지한
장애물의 횡방향 범위를 함께 추출하는 것은 새 센서가 아니라 같은 2D 스캔에서 더 많은
정보를 읽는 것으로 정당화됩니다.

**구현**: `front_gap()`이 이미 내부적으로 찾는 "가장 가까운 전방 장애물"의 나머지
정보를 버리지 않고 함께 반환하는 새 함수:

```
FrontObstacleInfo:
    gap_near: float   # 기존 front_gap과 동일
    gap_far: float    # 장애물 먼 쪽 면까지 거리
    y_lo: float        # 장애물 좌측 경계
    y_hi: float        # 장애물 우측 경계
(장애물이 감지 범위 밖이면 None)
```

**원칙 유지**: `improved/mpc.py`는 `scenario.obstacles`나 시뮬레이터 좌표를 전혀
참조하지 않고, `runner.py`가 매 step 계산한 `FrontObstacleInfo`(센서 출력)만
`solve()`의 새 인자로 받습니다 — 기존 front_gap(스칼라 1개)을 4개로 늘린 것뿐,
같은 위치·같은 원칙.

## 11. §11(구) 열린 논의 사항 — 해결됨(2026-09-23 재검토)

**최초 발견**: I1+I1b+I2(및 전체)는 충돌률·S3 실패율은 크게 개선하지만, REQ-MPC-04

에피소드, KEEP_L1/RETURN_TO_L2 상태).

**분해로 원인 규명**(`violation_breakdown`, `MEASURE_PLAN.md` 3단계 절 참고): 이
위반은 I2 자신의 여유 기준 미달(`i2_y_deficit`, 항상 0건)이 아니라 **I2가 활성인
동안 헤딩이 과도하게(최대 80°까지) 나빠지도록 허용해뒀던 MARGIN_I2의 최악 가정 자체가
너무 느슨**했던 것이 원인이었습니다.

**해결(I2', §1)**: I2 활성 구간에 `psi≥-20°` 하한을 함께 추가하고 마진을
`MARGIN_I2_PRIME=0.143m`로 재도출한 결과, **원래 제약 위반이 정확히 0으로 돌아가면서
(y_ok 0.981→1.000) 충돌률 0%·S3 실패율 0%는 그대로 유지**됩니다(dev 100 에피소드
+ dev S3 900격자 + dev S4 3프로파일×100 전부 확인). **I2'가 I2(wide)를 완전히
대체하는 개선안으로 확정**되며, 더 이상 열린 트레이드오프가 아닙니다.

**부수 확인(item 3)**: `maximum iterations reached` 근사해는 dev 전체에서 33건
발생했고 전부 하드 제약(|δ|≤25°, |Δδ|≤10°/step) 검사를 통과해 그대로 사용됐습니다

## 12. eval 직전 재검토(0번, 2026-09-23) — 허용오차 판정과 해결

**발견**: `MEASURE_PLAN.md`가 실행 전에 정한 허용오차(=OSQP eps_abs, 1e-4 rad≈0.0057°)
기준으로 I1+I1b+I2'+I3의 raw MPC 출력을 다시 판정하자, 조향각·조향변화율에서

"수치오차 수준"이라 표현한 것은 이 기준을 적용하지 않은 채 쓴 표현이었고, 정정합니다.

**원인**: 전부 `solver_status="solved"`. OSQP의 결합 종료 기준(`eps_abs+eps_rel·
max(‖Ax‖,‖z‖)`)에서 I1b의 무상한 슬랙이 같은 solve 안에서 커지면 `max(‖Ax‖,‖z‖)`가
커져, delta 경계처럼 무관한 행의 실질 허용오차까지 `eps_rel` 항을 통해 함께
느슨해짐(`SETTINGS_DECISION.md` §18 개선판 예외(2) 참고).

**해결(dev로만 검증, improved 전용 solver 설정)**: `eps_rel`을 baseline과 같은
1e-4에서 **1e-5**로 낮춤(`eps_abs`는 그대로). dev 100 에피소드+900격자+3프로파일×100
전부 재검증 결과 조향각·조향변화율·차로·헤딩 위반 **전부 0건**, 충돌률·S3 실패율은
그대로 0 유지, 최대 계산시간 42ms(20Hz 예산 50ms 안쪽). 부수 효과: `max_iter` 도달

실제 발동**함을 확인(§7 Stage 3에서 만든 안전판이 이번에 실제로 쓰임).

**결론: 0번 통과 — eval 실행 가능.** S5(제어 지연)는 `thesis_v2/improved/runner.py`에
