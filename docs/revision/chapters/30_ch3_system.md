# III. 시스템 설계

## 1. 전체 시스템 구조

시스템은 제출본과 같이 환경 모델, 의사결정(유한상태기계, FSM), 제어(횡방향·종방향), 정책 모듈로 구성된다. 제어 주기는
{{c:1}}이다.

재구현에서 제출본 구조에 더한 원칙은 하나이다. **제어기(FSM·MPC·속도 제어)는 센서 모델의 출력(front_gap, left_clear,
right_clear, ey_line)과 차량 자기 상태(y, ψ, v)만 입력으로 받고, 시뮬레이터 내부의 장애물 좌표를 직접 읽지 않는다.** 제출본은
이 경계를 서술하지 않았지만, 실제 차량에서 제어기가 받을 수 있는 정보만 쓰도록 강제해야 시뮬레이션 결과가 실차 구조와 대응하기
때문이다.

## 2. 시뮬레이션 환경

### (1) 도로와 시나리오

도로는 2차선 직선로이며 차선 폭은 {{c:2}}, 2차선(L2) 중심은 {{c:3}}, 1차선(L1) 중심은 {{c:4}}이다(RC카 차폭 {{c:5}} 기준).
차량은 L2에서 출발하고, 전방의 정지 장애물을 L1으로 회피한 뒤 L2로 돌아온다. 장애물 위치는 {{c:6}}, 초기 속도는 {{c:7}}의
균등분포이다.

재현 과정에서 제출본에 명시되지 않은 항목을 다음과 같이 정하였다(모두 `SETTINGS_DECISION.md`의 결정표에 근거).

- **장애물 위치의 기준점**: 차량 **전단**에서 장애물 앞면까지의 거리로 정하였다. 후륜 중심 기준으로 읽으면 하한에서 회피가 물리적으로
  불가능한 배치가 생기기 때문이다(`SETTINGS_DECISION.md` §12).
- **장애물 크기**: 제출본에 없어 차체와 같은 L×B로 두었다(§8).
- **초기 횡방향 위치 [개정]**: 제출본의 N(0, 0.05²)에는 절단 범위가 없다. 절단하지 않으면 {{n:rev2_prob}}의 확률로 초기 위치가
  L2 위치 제약(±0.15 m) 밖에서 뽑혀, 에피소드 시작부터 제약을 만족할 수 없다. 그래서 평균·표준편차는 그대로 두고
  {{c:45}}로 절단하였다. 이 보고서의 [개정] {{n:n_revision_items}}건 중 하나이다(IV장 1절, VI장 7절과 같은 기준 — "계산으로
  불가능이 증명된 명세만 수정").

### (2) 차량 모델

**표 1. 차량 파라미터(제출본과 동일).** [데이터: 설정값 | 호스트: 해당 없음 | 버전: baseline v1.1 | 커밋: C2]

| 파라미터 | 값 | 비고 |
|---|---|---|
| 축간거리 L | {{c:8}} | 고정 파라미터 |
| 차폭 B | {{c:9}} | 고정 파라미터 |
| 최대 조향각 | {{c:10}} | 고정 파라미터 |
| 속도 범위 | {{c:11}} | 고정 파라미터 |

차량 동역학은 제출본 식 (1)~(3)의 kinematic bicycle model을 Euler 적분으로 푼다(x, y는 후륜 중심). 속도는 동역학 없이 다음 스텝에
명령값이 바로 대입된다(제출본에 속도 동역학 서술이 없어 최소 가정).

### (3) 센서 모델

- **IR 센서**: {{c:13}}로 배치된 이진 센서 패턴을 차선 중심 오차 ey_line으로 바꾼다. 제출본에 변환식이 없어 패턴별 대응표를
  정의했고(`SETTINGS_DECISION.md` §9), 세 센서가 모두 선을 보지 못하면 "라인 미검출"로 처리한다.
- **LiDAR — front_gap**: 차량 통로(차폭 폭)와 횡방향으로 겹치고 아직 지나치지 않은 장애물까지, 차량 전단에서 잰 거리이다. 제출본에
  공식이 없어 정했으며, 1차 구현에서는 이미 지나친 장애물도 겹침만으로 거리 0이 되는 결함이 있어 종방향 조건(장애물 뒷면이 차량
  전단보다 앞에 있을 때만)을 더하였다(baseline v1.1).
- **LiDAR — left_clear / right_clear**: 옆 차선의 일정 종방향 창(차량 뒤쪽 G_SAFE_MIN부터 앞쪽 G_TRIG까지)에 장애물이 없으면 참이다.

### (4) 충돌 판정

제출본에는 충돌 판정 기준이 없다. 이 보고서는 **차체와 장애물을 회전 사각형으로 보고 겹침(분리축 정리)으로 판정**하며, 매
스텝 차량 상태를 갱신한 직후, FSM을 갱신하기 전에 검사한다. VI장의 충돌 수치는 모두 이 기준이다.

## 3. 소프트웨어 구조

제출본의 구조(SimulatedEnvironment, StateMachine, OSQPMPC, HierarchicalController, StudentPolicy)를 기능 단위로 따르되, 코드는
제출본 서술을 요구사항 명세로 삼아 처음부터 다시 작성하였다. 기존 코드는 비교용으로만 읽었고 복사하지 않았다.

1. 제출본을 {{n:n_req}}개의 요구사항 ID로 나누고(`repro/docs/SPEC.md`), 각 항목을 [정합](제출본 그대로)·[해석](모호 → 결정표)·
   [공백](없음 → 최소 가정)·[개정](실현 불가 증명 → 수정)으로 분류하였다.
2. 요구사항 ID별 단위 테스트 {{n:n_tests}}개를 두고, 측정 기준(판정 기준·seed·허용오차)을 실행 전에 고정하였다
   (`repro/docs/MEASURE_PLAN.md`).
3. 코드는 세 층으로 나뉜다 — `thesis_v2/baseline/`(제출본 설계의 정합 재구현, 개선 단계 동안 동결), `thesis_v2/improved/`(VI장
   6절의 개선판), `thesis_v2/improved/student_i4/`(VI장 4절·7절의 Student).
4. MPC가 매 스텝 낸 원출력, 후처리 후 출력, 솔버 상태, fallback 사용 여부를 모두 기록해 "제약을 만족하는 조향각을 계산하는가"를
   스텝 단위로 검증할 수 있게 하였다.
