# VI. 반복(iteration) 기록과 버그 수정 이력

이 장은 평가 데이터를 실행하기 **전에** 탐지기와 도구를 바꾼 기록이다. 바꾼 이유는 모두 개발(dev) 데이터나 정상 데이터에서 발견했으며, 이전 반복의
모델·임계값·결과는 지우지 않고 보존하였다. 평가 데이터(AE·AC)는 각각 마지막 반복의 동결 커밋에 1회만 실행하였다.

**표 6-1. 반복과 수정 요약.** [데이터: AN · AT · AD | 호스트: H1 · H3 · H4 | 버전: 각 행 | 커밋: K2 · K3 · K4 · K5]

| 순서 | 무엇을 바꿨나 | 계기(발견 데이터) | 평가 결과에 쓰인 버전 |
|---|---|---|---|
| iteration 1 | A(6채널)·B1·B2 첫 구현, 정상 데이터 = 원거리 시나리오만 | — | 아니오(보존) |
| iteration 2 | 학습·임계값 정상 데이터에 좌측 장애물 시나리오 추가, A·B 임계값 재결정, B 재학습 | dev에서 B의 좌측 장애물 정상 오경보 | B1·B2 |
| iteration 3 | A에 ir_miss 채널 추가(A만) | dev에서 B2는 잡고 A는 못 잡은 ir_dropout | A |
| 동결 전 수정 | σ 전달 버그 수정(도구), 하이브리드 학습 | 비정상적으로 큰 σ=0.05 임계값 | A·하이브리드 |
| 기록 수정 | 환경 기록의 git dirty 값 | 오프라인 평가 env.json | (결과 무관) |
| 검증 도구 | 폐루프 `--check` 불일치 진단 분리, 부분 확인 | dev `--check` 1회 불일치 | (결과 무관) |

## 1. iteration 1 → 2: 정상 데이터 범위의 공백

iteration 1에서는 B의 학습과 모든 탐지기의 임계값에 **원거리 시나리오 정상 주행만** 썼다. 평가에는 좌측 장애물 시나리오의 정상 주행(SAFE_STOP으로 끝남)도
들어가는데, 이 운행 모드가 정상 데이터에 없었다. dev 점검에서 B의 좌측 장애물 정상 오경보로 이 공백이 드러났다. 같은 seed 대역에 좌측 장애물 정상 주행을
추가하고(iteration 2), B의 특징·구조·학습 설정은 바꾸지 않았다.

**표 6-2. 정상 데이터 범위에 따른 B의 dev 결과(각 100회 중 경보·탐지).** [데이터: AD | 호스트: H1 | 버전: B iteration 1 · 2 | 커밋: K2]

| 실행 | B1 it1 | B1 it2 | B2 it1 | B2 it2 |
|---|---|---|---|---|
| 정상 좌측 장애물 경보 | {{a:dev_b1_it1_none_leftobs}} | {{a:dev_b1_it2_none_leftobs}} | {{a:dev_b2_it1_none_leftobs}} | {{a:dev_b2_it2_none_leftobs}} |
| 정상 원거리 경보 | {{a:dev_b1_it1_none}} | {{a:dev_b1_it2_none}} | {{a:dev_b2_it1_none}} | {{a:dev_b2_it2_none}} |
| lidar_freeze | {{a:dev_b1_it1_lidar_freeze}} | {{a:dev_b1_it2_lidar_freeze}} | {{a:dev_b2_it1_lidar_freeze}} | {{a:dev_b2_it2_lidar_freeze}} |
| lidar_dropout | {{a:dev_b1_it1_lidar_dropout}} | {{a:dev_b1_it2_lidar_dropout}} | {{a:dev_b2_it1_lidar_dropout}} | {{a:dev_b2_it2_lidar_dropout}} |
| steer_delay | {{a:dev_b1_it1_steer_delay}} | {{a:dev_b1_it2_steer_delay}} | {{a:dev_b2_it1_steer_delay}} | {{a:dev_b2_it2_steer_delay}} |

- 좌측 장애물 정상 오경보는 줄었다. 그러나 B1은 임계값이 좌측 장애물 정상 주행의 높은 점수로 정해져 고장을 거의 놓치게 되었다(steer_delay
  {{a:dev_b1_it1_steer_delay}} → {{a:dev_b1_it2_steer_delay}}). B2는 반대로 드문 패턴에 민감해져 무해 대조군 ir_dropout을 모두 탐지하게 되었다.
- 탐지기 설계가 아니라 **정상 데이터를 어디까지 보여줬는가**가 B의 결과를 크게 바꾼다. 이것 자체를 결과로 보고하고, B를 그에 맞춰 고치지 않았다.
  A는 물리 모델 잔차라 정상 데이터는 h에만 영향을 주었다({{a:h_a_it1}} → {{a:h_a}}).

## 2. iteration 3: A의 ir_miss 채널

A의 ey 잔차는 "측정과 예상이 둘 다 검출"일 때만 정의되어, IR이 미검출(None)이 되는 ir_dropout을 볼 수 없었다. dev에서 B2가 ir_dropout을 잡는 것을 보고
"예상은 검출인데 측정은 미검출"이라는 관측 가능한 정보를 A가 쓰지 않고 있음을 확인해 ir_miss 채널을 더했다. dev에서 A의 ir_dropout 탐지가 100회 중
{{a:dev_a_it2_ir_dropout}}회에서 {{a:dev_a_it3_ir_dropout}}회로 바뀌었다. 다른 고장과 정상 오경보는 그대로였고 h도 바뀌지 않았다. ir_dropout은 무해 고장이라
이 변경은 폐루프에서 P1의 불필요 정지를 늘리는 쪽으로 작용한다(V장).

## 3. σ 전달 버그(동결 전 발견·수정)

σ_gyro 민감도용 임계값을 σ = 0.05 °/s로 정했더니 h = {{a:bug_h_sg005}}로 비정상적으로 컸다(σ = 5에서는 {{a:bug_h_sg5}}). ψ 잔차가 가우시안 노이즈뿐이라면
z-정규화 후 h는 σ와 무관해야 한다.

- **잔차 계산은 정상이었다.** 노이즈를 거의 0으로 둔 정상 주행에서 ψ 잔차는 부동소수점 오차 수준이었다.
- **원인**: 임계값·dev 도구가 σ를 탐지기의 정규화에만 넘기고 시뮬레이션의 자이로 노이즈 주입에는 넘기지 않았다. 그래서 주입 노이즈는 항상
  기본값 σ = 1로 들어갔다. 실제 노이즈를 20배 작은 가정 σ로 나눈 z가 CUSUM으로 누적되어 h가 커졌다. σ = 1(주 조건)은 기본값과 같아 영향이 없었다.
- **수정 후**: 두 σ의 h가 {{a:fix_h_sg005}}, {{a:fix_h_sg5}}로 주 조건 h({{a:h_a}})와 같아졌다. dev σ 민감도도 버그 상태(고장 탐지 900회 중 σ=0.05
  {{a:bug_dev_sg005_fault}}회, σ=5 {{a:bug_dev_sg5_fault}}회·정상 오경보 {{a:bug_dev_sg5_normal}}회)에서 수정 후 두 σ 모두 {{a:fix_dev_sg005_fault}}회로 바뀌었다.
- 버그 상태의 결과 폴더는 증거로 보존하고 "폐기"로 표시하였다. 오프라인 평가는 수정 후 임계값만 썼다(IV장 표 4-4).

## 4. 기록·검증 도구의 수정

- **환경 기록의 git dirty 값**: 결과 폴더의 `env.json`이 결과 파일을 다 쓴 뒤 git 상태를 읽어, 자기 결과 파일 때문에 dirty로 기록되었다. 오프라인 평가 실행
  자체는 실행 전 확인에서 깨끗한 동결 커밋이었고 결과는 유효하다. 이후 실행은 스크립트 시작 시점의 git 상태를 기록하도록 고쳤다. 기존 폴더는 수정하지 않았다.
- **폐루프 `--check` 불일치(원인 미확정)**: dev 폐루프 결과의 결정성 재계산에서 탐지기 없는 조합(P0)의 episodes 파일이 1회 불일치하였다(노트북 H1).
  같은 PC의 단독 재계산 3회는 모두 일치하였다. v2 MPC의 OSQP 시간 제한이 실행 중 CPU 부하로 발동했다는 가설은 부하 실험에서 재현되지 않았다.
  이후 "실행 중 같은 PC에서 다른 작업을 하지 않는다"는 규칙을 사전 선언하고, MPC 시간 제한 발동 횟수를 결과와 분리해 기록하였다. 이 규칙 아래에서
  부분 확인(H1·H4)과 6개 조합 전체 확인(H4)이 모두 일치하였다. 원인은 미확정으로 남긴다. 폐루프 평가 실행에서 시간 제한 발동은 {{a:cl_tlhit}}회였다
  (최대 solve 시간 {{a:cl_maxsolve}}, 참고치).
- **사전 선언 위반 1건**: 폐루프 결과 분류를 6종으로 선언하고 "그 밖의 결과가 나오면 버그로 본다"고 정했으나(`DESIGN.md` §24), 기존 runner에서
  물려받은 "미정착" 분류를 빠뜨렸다. 평가에서 1건이 나왔고, 재분류하지 않고 기타로 분리 보고하였다(V장 Q1).

## 5. 재현성 확인

- 테스트 {{a:n_tests_total}}개(기존 {{a:n_tests_base}} + 이상탐지 {{a:n_tests_anomaly}})가 통과한다. 이상탐지 코드를 붙여도 기존 golden(조향각 최대 차이 0)이 유지된다.
- 다른 PC(H4)에서 IF를 다시 학습해도 고정 입력 점수가 같았다(III장). dev 폐루프 결과는 H3에서 만들고 H4에서 재계산해 결과 파일 전체가 일치하였고,
  노트북(H1)의 부분 확인(P0·P2_A)도 일치하였다(노트북 전체 확인 1회의 P0 불일치는 4절). 이것이 폐루프의 **다른 PC 간** 재현 근거이다.
- **오프라인 평가 결과의 재현 확인(다른 PC)**: H3에서 만든 오프라인 평가 결과 폴더(AE)를 H4에서 `--check`로 다시 계산하였다. 비교 대상 {{a:offchk_same}}개 파일
  (탐지기 4종 episodes, σ 일치 2종·불일치 3종 episodes, `summary.json`)이 모두 일치하였다(종료 코드 {{a:offchk_exit}}, {{a:offchk_time}}).
  실행 코드는 HEAD(`{{a:offchk_head}}`)였다. 동결 커밋 K4 이후 오프라인 계산 경로의 코드는 바뀌지 않았다(폐루프용 클래스 추가와 환경 기록 시점 수정뿐,
  `git diff`로 확인). `--check`는 비교 직후 임시 파일을 지우므로 평가 결과 폴더는 바뀌지 않는다.
- **폐루프 평가 결과의 재현 확인(같은 PC)**: H4에서 만든 폐루프 평가 결과 폴더(AC)를 같은 H4에서 `--check`로 다시 계산하였다. 비교 대상
  {{a:clchk_same}}개 파일(6개 조합 episodes, `summary.json`)이 모두 일치하였다(종료 코드 {{a:clchk_exit}}, {{a:clchk_time}}). 실행 코드는 HEAD(`{{a:clchk_head}}`)였고,
  동결 커밋 K5 이후 바뀐 것은 설계 기록 문서뿐이다(`git diff`로 확인). 재계산 중 MPC 시간 제한 발동은 {{a:clchk_tlhit}}회, 최대 solve 시간은
  {{a:clchk_maxsolve}}였다(참고치, 비교 대상 아님). 진단값은 `_check_diag_timing.csv`로 결과 폴더에 남고 그 밖의 결과 파일은 바뀌지 않는다.
- 두 확인은 성격이 다르다. 오프라인 평가는 **다른 PC 간** 재현(H3 → H4)이고, 폐루프 평가는 **같은 PC 재실행**(H4 → H4)이다. 폐루프의 다른 PC 간
  재현은 dev 결과(위 둘째 항목)로만 확인하였다.
